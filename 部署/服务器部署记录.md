### 6. 配置 OpenResty 反向代理（1Panel 方式）

1Panel 装的 OpenResty 是**容器 + host 网络模式**（进程直接监听宿主机 80/443），配置文件在宿主机上：

```
/opt/1panel/apps/openresty/openresty/conf/conf.d/
├── 00.default.conf   # 兜底 server（server_name _），返回 404
├── default.conf      # server_name 127.0.0.1，含 acme-challenge
└── zhimai.conf       # ← 新增：把 80 反代到 8099
```

`zhimai.conf` 内容：

```nginx
server {
    listen 80;
    server_name 47.96.253.135;

    charset utf-8;
    client_max_body_size 50m;

    location / {
        proxy_pass http://127.0.0.1:8099;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 300s;
    }
}
```

重载（**容器名要精确**，先用 `docker ps` 查）：

```bash
docker exec 1Panel-openresty-XXXX openresty -t          # 先验语法
docker exec 1Panel-openresty-XXXX openresty -s reload
```

因为 OpenResty 是 host 网络，容器内 `127.0.0.1:8099` 就等于宿主机，能直连到 zhimai 容器（zhimai 是 bridge + docker-proxy 映射）。

### 7. 配置 HTTPS（IP 证书）

**为什么能用 IP 上 HTTPS**：Let's Encrypt 自 2026-01-15 起给公网 IP 签证书，但强制 `shortlived` profile，有效期 160 小时（约 6.7 天）。

**为什么必须设 `default_server`**：浏览器用 IP 访问 HTTPS 时**不发送 SNI**（SNI 字段本义是主机名，IP 字面量通常不发）。没有 SNI，nginx 只能选该端口的默认 server —— 而 1Panel 的 `00.default.conf` 正是 443 的隐式默认，用的是空占位证书。所以必须在自己的 server 块显式声明 `default_server`，否则会命中错误证书。

**步骤**：

```bash
# 1. 装 acme.sh（单脚本，装完自动排 crontab）
curl -s https://get.acme.sh | sh

# 2. 注册 Let's Encrypt 账号（可无邮箱）
~/.acme.sh/acme.sh --register-account --server letsencrypt

# 3. 申请 IP 证书
~/.acme.sh/acme.sh --issue \
  -d 47.96.253.135 \
  --webroot /opt/1panel/apps/openresty/openresty/root \
  --server letsencrypt --cert-profile shortlived

# 4. 安装证书并登记「续期成功后自动 reload」
~/.acme.sh/acme.sh --install-cert -d 47.96.253.135 \
  --key-file       /opt/1panel/apps/openresty/openresty/conf/conf.d/ssl/47.96.253.135.key \
  --fullchain-file /opt/1panel/apps/openresty/openresty/conf/conf.d/ssl/47.96.253.135.crt \
  --reloadcmd      "sudo -n docker exec 1Panel-openresty-W22x openresty -s reload"
```

`zhimai.conf` 完整版（80 只做验证 + 跳转，443 主入口）：

```nginx
server {
    listen 80;
    server_name 47.96.253.135;

    location ^~ /.well-known/acme-challenge/ {
        root /usr/share/nginx/html;
        default_type text/plain;
        allow all;
    }
    location / { return 301 https://$host$request_uri; }
}

server {
    listen 443 ssl http2 default_server;   # ← default_server 是关键，见上文
    server_name 47.96.253.135;

    ssl_certificate     /usr/local/openresty/nginx/conf/conf.d/ssl/47.96.253.135.crt;
    ssl_certificate_key /usr/local/openresty/nginx/conf/conf.d/ssl/47.96.253.135.key;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_ciphers         HIGH:!aNULL:!MD5;
    ssl_session_cache   shared:ZhimaiSSL:10m;

    charset utf-8;
    client_max_body_size 50m;

    location / {
        proxy_pass http://127.0.0.1:8099;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 300s;
    }
}
```

**证书放哪**：`/opt/1panel/apps/openresty/openresty/conf/conf.d/ssl/`
理由：容器挂载了 `conf.d`（映射到 `/usr/local/openresty/nginx/conf/conf.d`），而 nginx 只 `include conf.d/*.conf` —— `ssl/` 子目录既不会被加载，也不会被 web 暴露，**私钥安全**。

**申请时的两个坑**：
1. `--webroot` 目录默认属主是 root，acme.sh 以 admin 身份跑会 `Permission denied`。先 `sudo chown -R admin:admin <webroot>/.well-known`。
2. 必须显式 `--server letsencrypt`：acme.sh 默认 CA 是 ZeroSSL，而 **ZeroSSL 不支持 IP 证书**。

**自动续期**：acme.sh 安装时写入 crontab（每天 3:51 / 9:51 / 15:51 / 21:51 四次）；`--install-cert` 登记的 `--reloadcmd` 会在续期成功后自动执行。证书配置里保存了 `Le_Certificate_Profile='shortlived'`，续期会带上必需 profile（不带会被 CA 拒绝）。

**验证结果**：

| 检查项 | 结果 |
|---|---|
| `http://47.96.253.135/` | 301 → HTTPS |
| `https://47.96.253.135/` | **200，`ssl_verify_result=0`**（证书链被信任，浏览器无警告） |
| 不带 SNI 时返回的证书 | Let's Encrypt YE1，SAN = `IP:47.96.253.135` |
| `/api/status` 的 `callback_uri` | `https://47.96.253.135/auth/zhihu/callback` |
| `/api/status` 的 `invalid` | `[]`（无非法配置，HTTPS + IP 通过项目校验） |
| 跨源校验 | 合法 Origin 放行；`https://evil.example` → **403** |

## 四、踩到的坑（按排查成本排序）

### 坑 1 · 镜像加速器「假可用」——最费时间

1Panel 安装时写入 `daemon.json` 的 `registry-mirrors` 是 `https://docker.1panel.live`。

**它 curl 返回 200，但 Docker 用不了**：`docker pull hello-world` 直接回退到 `registry-1.docker.io` 然后超时（12 秒无响应）。表面现象是"Docker Hub 拉不动"，很容易误判成网络故障。

实测 6 个源：

| 源 | 结果 |
|---|---|
| `docker.1panel.live` | ❌ curl 200 但 Docker 用不了 |
| `docker.m.daocloud.io` | ✅ 0.05s |
| `docker.1ms.run` | ✅ 0.11s |
| `docker.xuanyuan.me` | ✅ 0.88s |
| `registry.cn-hangzhou.aliyuncs.com` | ✅ 0.05s |
| `hub-mirror.c.163.com` | ❌ 000，已停服 |

**教训**：判断加速器是否可用，不能只看 curl 通不通，要看 `docker pull` 能不能真的走通。

### 坑 2 · 中文目录名导致 Compose 起不来

项目目录名是「知乎」，`docker compose` 报 `project name must not be empty`。

**解法**：compose 顶层显式写 `name: zhimai`。

### 坑 3 · `.dockerignore` 的 `*.md` 会误伤知识库

第一版写了 `*.md`，会把 `笔记库/wiki/` 下 37 份 Markdown 正文全排除掉 —— 那是 `/api/笔记` 的运行时数据，镜像里没了等于知识库空了。

**解法**：逐一点名根目录的文档，绝不用通配符。

**验证方法**：容器起来后看日志 `索引已载入：27 个分节`，与本地基线一致即证明数据完整。

### 坑 4 · 大陆服务器 pip 慢

`pypi.org` 直连实测耗时 12 秒。已在 Dockerfile 里加 `ARG PIP_INDEX`（默认官方源），构建时通过 `build.args` 传国内源。换成阿里云源后，依赖安装只花 9 秒。

### 坑 5 · 本机代理会污染测试结果

本机开着代理（`HTTP_PROXY=http://127.0.0.1:7890/`）时，`curl http://<服务器IP>:8099` 会返回 **502**（代理返回的），看起来像服务器出问题。

**解法**：测试服务器直连要加 `--noproxy '*'`。

> 注意区分：**服务器拉镜像慢和本机代理无关**（服务器是独立主机）；但**本机测服务器端口时，代理确实会干扰**。

### 坑 6 · 端口放行是两层

1Panel / Docker 里看到端口在监听，**不等于外网能访问**。云厂商安全组是独立的一层，必须在控制台另行放行。

## 五、这台机器的定位

杭州属**大陆地域**，因此：

- 大陆服务器 + 域名 → **必须 ICP 备案**（阿里云备案系统不支持用 IP 备案）
- 未备案的 80/443 会被拦截
- 本项目回调**强制 HTTPS** → IP 证书需要 80/443（被拦）→ 域名证书需要备案（赶不上 9/15）

**结论：这台机器适合当验证机，不适合作为最终 Demo。**

另：内存 896MB、无 Swap，1Panel 自身已占约 400MB，余量偏紧。

### 7.1 修掉一个真 bug：登录后进不去收藏夹页

**症状**：登录成功后进不了「收藏夹」列表页，按账号收录的摘要库永远是空的——服务器上 `find /app -name "*.sqlite3"` 无任何结果。

**根因（两处叠加，缺一不可）**

1. 账号页由 `create_app` 挂在 `/`；而一体化入口（`工具/应用.py`）把 `/` 重建成知识库首页，并在复制路由时**跳过了授权应用的 `/`** → 账号页在一体化入口下**根本没有路由**。
2. `/login` 在会话有效时 `303` 跳走 → 已登录用户同样进不去；而唯一指向账号页的链接都写着 `href="/"`，落回共享演示库。

**修法**：新增独立路由 `ACCOUNT_PATH = "/account"`（`工具/zhihu_oauth/app.py`）

- 已登录 → 渲染账号页（把 `data-default-return-to` 覆写为 `/account`）
- 未登录 → `303 /login?returnTo=/account&result=<code>`
- 一体化入口只跳过 `/`，所以 `/account` 会被自动复制过去，**两个入口同时生效**
- 配套改动：`workspace_ui.py` 两处 `href="/"` → `/account`；`工具/应用.py` 知识库首页右下角用户条新增「我的收藏夹」入口

### 7.2 数据持久化：容器重建不再清空用户摘要

`工具/zhihu_oauth/workspace.py` 的 `DEFAULT_DB` 是 `/app/数据/用户工作区.sqlite3`，原先**只存在容器可写层**——每次 `--build` 或 `down` + `up` 都会清空按账号收录的摘要。

`docker-compose.yml` 增补：

```yaml
    volumes:
      - ./数据:/app/数据
```

`.dockerignore` 同步排除 `数据/`（宿主机运行时数据不进镜像）。

**验证**：`docker inspect` 的 Mounts 为 `/opt/zhimai/数据 -> /app/数据`；容器内 `touch /app/数据/_写入测试` 成功。

### 8.2 本轮新增路由（一体化入口自动继承）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/settings` | 凭证设置页（需登录；未登录 `303 → /login?returnTo=%2Fsettings&result=login_required`） |

### 16.2 四个缺陷与修法

| # | 缺陷 | 后果 | 修法 |
| --- | --- | --- | --- |
| 1 | 指纹是"整夹快照**覆盖**写" | 某次拉到的条目比上次少（列表上限、上游波动、用户在知乎取消收藏）→ 指纹缩水 → 掉出快照的条目下次又被当新内容 | `记录归并条目` 改为**并集累加**（单事务内读-并-写；空输入直接返回，不清空旧值） |

| 3 | 老数据没有指纹 | 升级后第一次点「处理」把老文章全重跑一遍（本次事故） | 新增 `WorkspaceRepository.块的来源网址(uid, 夹)`：用已有块里记的来源网址**反查**条目，认出来的直接跳过，**零调用** |
